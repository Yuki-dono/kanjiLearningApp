Systems & data storage

KanjiLearn is a local-first site: everything the learner does is written to this device first, then mirrored to their account through our own API so progress follows them between phone, tablet and PC. Supabase authenticates; server/app owns the data.

What lives where

One row per concern. Everything below the line only exists once the learner signs in.

Local key Shape Cloud table How it merges
kanji-daily-v2 · settings level, goal, scope[] study_settings Whole row, replaced on change — newest updated_at wins.
kanji-daily-v2 · srs one entry per kanji: reps, lapses, ease, interval, due srs_cards Per changed character, batched 500 at a time. Never regresses — the card with more reviews wins.
kanji-daily-v2 · days per day: newChars[], graded{} study_days Per changed day, unioned — another device can add grades but never erase yours.
kanji-daily-v2 · streak streak, lastActive profiles Recomputed on the server from the rows below — the browser no longer reports XP or streak.
kanji-best best percentage per quiz mode quiz_scores Local only. The account keeps the full history of every attempt instead.
kanji-custom your own vocabulary entries custom_words Upserted on (user_id, word) — same word updates, never duplicates.
kanji-theme light / dark — Device preference. Deliberately never synced.

Reset is honest about it: it clears localStorage and deletes this account's rows in srs_cards, study_days, quiz_scores and custom_words, then zeroes the profile counters — so a second device can't resurrect progress the learner asked to erase.

When a sync happens

Pull always runs before push, so a device merges before it writes.

5s after any change every 2 min if dirty tab regains focus browser back online sign-in / app boot (full) leaving the page
  • 1Boot. The ten JSON files load in parallel into memory; nothing is written.
  • 2Study. Every grade updates daily.srs, saves to localStorage and marks that character dirty.
  • 3Pull. Six tables are read in parallel and merged into local state.
  • 4Push. Only dirty pieces are upserted; quiz results are inserted from a queue.
  • 5Offline? The app never blocks — it keeps working and the dirty flags wait for the next attempt.

Privacy & safety rails

Two layers: database constraints in supabase-schema.sql, and request scoping in server/app.

  • ARLS on all six tables. Reads and writes are filtered to auth.uid(). Defence in depth — the API never relies on it, but it stays on.
  • BEvery request scoped server-side. The API verifies the access token against Supabase's signing keys and reads the account from the token alone. A user_id in a request body is ignored and overwritten.
  • CThe service_role key never ships. It bypasses RLS and lives only in server/.env. The browser only ever holds the public anon key, which is used to sign in and nothing else.
  • DTotals are computed, not reported. XP and streak are derived from the study rows on the server, so editing localStorage can't inflate them.
  • ECascade deletes. Deleting the account in Supabase removes every study table automatically.
  • FExport / import. A JSON backup of all three local keys can be downloaded and restored.
